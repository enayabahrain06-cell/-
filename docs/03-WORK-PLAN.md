## Approved changes folded into the plan (2026-09-27)

1. `packages.name_ar` / `name_en` (`name` stays the fallback) — done in migrations.
2. `registration_requests.waitlist_position` — assigned on waitlist, re-packed on accept/reject (step 2.2).
3. `lesson-sessions:generate` artisan command + daily scheduler entry generating 8 weeks ahead. On lesson change: future sessions **without attendance** are regenerated; sessions with attendance are never deleted or moved (step 2.3).
4. `refunds` table linked to the refund wallet transaction; `payments.amount_fils` is validated positive (step 2.8).
5. `media` is the single source of truth; path columns dropped from certificates, exam_attempts, exam_answers, payments. `students.photo_path` / `photo_thumb_path` stay as caches (list/roster rendering per row).
6. Guardian phone lives on the guardian `users` row; a `UserObserver` propagates changes to `students.guardian_phone` for all children (step 2.2).
7. All eight design decisions confirmed.
8. Delivery gate: the GitHub Actions matrix (sqlite, mysql, pgsql) must be green; each module summary includes the run link.

**Framework (approved 2026-09-27):** the backend is on **Laravel 12.x** (PHP 8.2+). The original brief said Laravel 11, but Composer blocks every 11.x release for unpatched security advisories; the user approved Laravel 12 and asked not to downgrade.

**Delivery gate:** the GitHub Actions workflow (`.github/workflows/ci.yml`: SQLite, MySQL 8, PostgreSQL 15) stays in the repo. No phase counts as delivered until the MySQL and PostgreSQL runs pass; they run as soon as the GitHub remote exists.

## Cross-cutting decisions (please confirm or change)

1. **Table name** `lesson_sessions` instead of `sessions` (Laravel reserves `sessions`).
2. **Guardian accounts** are `users` rows found-or-created by guardian phone on acceptance, so siblings share one guardian login. `students.guardian_user_id` links them.
3. **Teachers** get a `teachers` profile table (gender, specialization) in addition to the `teacher` role, used by the lottery and the teachers screen.
4. **Sessions are materialised**: a `lesson_sessions` row is generated per lesson per day (by a scheduled command and on lesson save), so attendance, reminders, overrides and reports all key off a concrete date.
5. **Allocations** are recorded in `invoice_payments`, so a receipt can show which invoices it settled and the finance report reconciles exactly.
6. **Photos**: `students.photo_path` / `photo_thumb_path` cache the two variant paths; the `media` table holds the rows (collections `photo` and `photo_thumb`).
7. **Bilingual data**: only UI and templates are translated; user-entered content is stored once.
8. **Marks are integers**; `evaluations` scores are 0–10 integers.
